# SCS.md

How to build inside one self-contained system (SCS) in Dataroom: where each piece of code goes,
how it talks to other systems, and what a change must carry. Read it before adding or moving code
in any `services/<name>` or `plugins/<name>`. It adds to `CLAUDE.md`, `docs/architecture.md` and
`docs/conventions/`; where they differ on an SCS's internal layout, this file wins.

## What an SCS is

- One directory that owns its tables, its backend and, when it has one, its UI.
- `services/<name>` are core systems every workspace gets; `plugins/<name>` are features a space
  opts into. `services/dataroom` and `services/assessment` are not plugins: their `ui/` is a
  library the console renders as fixed routes (`data-rooms/*`, `assessments/*`), with no bundle.
- Its backend talks to other systems only over gRPC and typed Kafka events. It may depend on
  another system's `<name>-sdk` only, never on its server crate, and reads another system's
  table only through a `#[postgres(skip_schema)]` mirror.
- The browser reaches it only through `services/bff` (`CoreCall` for workspace, `PluginCall` for
  plugins). Adding a method never adds a BFF route.

## Directory layout

```
<name>/
├── Cargo.toml                              backend crate; its workspace has sdk/ as a member
├── sdk/                                    <name>-sdk: the contract other SCSs use, proto/ + build.rs
├── package.json · meta.ts · vite.config.ts UI package and bundle meta (bundle SCSs)
├── public/                                 static assets copied into the bundle
├── Makefile · Dockerfile · .env.sample     build and run
├── README.md                               the SCS README (shape in CLAUDE.md)
├── src/                                    backend, nothing else
└── ui/                                     frontend, nothing else
```

The root holds only build and contract files plus `sdk/`; an SCS without an sdk keeps
`build.rs · proto/` at the root. Backend code never sits outside `src/`; UI code
never sits outside `ui/`.

## Backend: `src/`

```
src/
├── main.rs · lib.rs · config.rs · error.rs
├── grpc/        service.rs, auth.rs, methods/<resource>.rs
├── api/         <resource>/<handler>.rs (HTTP services only)
├── models/      one #[derive(PostgresEntity)] per file, skip_schema mirrors alongside
├── services/    business logic and outbound clients
├── types/       DTOs shared by grpc/ and api/; ts-rs behind the ts-bridge feature
└── events/      link() and consumers; produced event schemas live in sdk/
```

- Name modules after the domain aggregate, never after the transport.
- Errors are one `ServiceError` enum in `error.rs`, or in `sdk/` when the SCS has one; the derive
  produces the `tonic::Status`. See [`ERROR.md`](ERROR.md).
- Unit tests go in `tests.rs` beside the module (`foo.rs` → `foo/tests.rs`).
- Auth is checked per method in the SCS itself, even when the BFF already checked the workspace.

## Frontend: `ui/`

```
ui/
├── index.tsx        bundle entry: imports styles.css, re-exports the Plugin (bundle SCSs)
├── plugin.tsx       { mount, unmount, update } and the React root (bundle SCSs)
├── app.tsx          root component: reads the route and renders a page
├── route.ts         parse and build the SCS's URLs
├── rpc.ts           typed wrappers over host.call, one per method
├── i18n.ts          en/ko strings
├── styles.css       the SCS's Tailwind entry (bundle SCSs)
├── pages/           one screen per route
├── components/      components shared by pages
├── hooks/           custom React hooks, one per file
├── utils/           plain functions: formatting, mapping wire data to view data, errors
└── types/           generated by make gen-ts; gitignored, never hand-edited
```

### pages/

- One file or folder per screen `route.ts` can resolve (`pages/room.tsx`,
  `pages/room-assessment/`).
- A component only one page uses lives in that page's folder. Once a second page needs it, it
  moves to `components/`.

### components/

- Presentational and interaction components shared by two or more pages, grouped by area in
  subfolders when there are many (`components/evidence/`, `components/dialogs/`).
- A component gets its data from props or from a hook in `hooks/`. It never defines a custom
  hook inline and never calls `rpc.ts` in its render body.
- Components a second SCS's bundle needs go to `packages/components`, in their own PR.

### hooks/

- Every custom hook lives in `ui/hooks/`, one per file: `hooks/use-<name>.ts` exporting
  `use<Name>` and the interface it returns. This includes hooks only one component uses and
  hooks copied from elsewhere. No `function useX` in a component, page or `utils/` file.
- A hook owns the server state it loads and the mutations on it. A mutation method on the hook
  calls the server, then updates the hook's state so every consumer re-renders, and refetches
  when the server may have changed more than the reply shows.
- Plugin UIs: hooks call `rpc.ts` (`host.call`). They never import react-query or
  `@biyard/bff-client` hooks. A mutation writes the server's reply into local state and bumps a
  reload nonce.
- Host pages (`services/workspace`): server state comes from the generated `@biyard/bff-client`
  hooks. Hand-written hooks wrap them and use `mutate` and query invalidation. They live in
  `ui/hooks/` like everywhere else.
- Components share one hook instance by lifting it to the nearest common parent and passing the
  result down, not by calling the same hook twice.

### utils/

- Plain TypeScript with no React import: formatters, view-model mapping from `types/`,
  error description, upload and hashing helpers.
- One topic per file (`utils/evidence.ts`, `utils/errors.ts`), no `utils.ts` or `helpers.ts`
  catch-all.

### types/

- Generated wire types only. `make gen-ts` wipes and rewrites it; it is gitignored.
- A hand-written UI-only type sits with the module that produces it: a hook's return type in the
  hook file, a view model in its `utils/` file. There is no hand-written `types.ts`.

### General

- Files kebab-case, components PascalCase, hooks `use` + PascalCase.
- Tests sit next to the file under test as `<file>.test.ts`.
- Other SCSs import this SCS's UI only by the paths it already exposes
  (`@biyard/plugin-dataroom/ui/...`). Moving such a file changes the importing SCS too; count it
  as a secondary change.
- Host UIs (`services/workspace/ui`, `services/landing/ui`) keep their App Router `pages/` tree
  from `docs/conventions/feature-module-structure.md`, but put hooks in `ui/hooks/` and plain
  helpers in `ui/utils/` instead of `ui/lib/`; `lib/` keeps only providers and `routes.ts`.
- Existing SCSs that predate this layout move a file into place when a PR touches it. Moving a
  whole SCS is its own refactor PR, not part of a feature PR.

## Talking to other systems

| Need | How |
|---|---|
| Browser calls this SCS | `PluginCall` / `CoreCall` through the BFF dispatchers; the UI uses `host.call` or `@biyard/bff-client` |
| This SCS calls another | the callee's `<name>-sdk` client (`grpc-client`) wrapped in `src/services/`, internal methods authenticated with `dr-server-key` |
| Tell others something happened | `#[event]` producer with its schema in the producer's sdk; consumers dedupe on `event_id` |
| Use another SCS's domain types | depend on its `<name>-sdk`, schema-only (no heavy features) |
| Read another SCS's data | `skip_schema` mirror with a strict subset of the owner's columns |
| Show another SCS's UI | import its exposed UI module (as dataroom does with the assessment renderer) and call through the same host |

## SDK crate

An SCS that exposes a contract to other SCSs has `<name>/sdk/`, a package named `<name>-sdk`.

- It holds the SCS's whole public contract: domain schema types other SCSs use, the event schemas
  it produces, its gRPC proto (`sdk/proto/`, compiled by the sdk's `build.rs`) with generated
  client and server, and its `ServiceError` enum.
- `packages/` keeps only code owned by no single SCS. Producer event crates
  (`packages/events/<producer>`) and per-service protos in `packages/dataroom-sdk` move into the
  owning SCS's sdk.
- Contract only: pure domain types plus behaviour attached to them. No DB access, no runtime
  (tokio), no Kafka publishing, no other server logic.
- Heavy parts sit behind features (`events`, `grpc-client`, `grpc-server`, `postgres`,
  `ts-bridge`) so schema-only consumers do not pay for them.
- The `ServiceError` enum is shared by sdk and server. Never add a separate sdk error type: codes
  and status are part of the contract.
- Event schemas are producer-owned: the event struct and every type in its fields are defined in
  the producer's sdk. Never import a consumer's or another SCS's type to build an event; to carry
  a value received from another SCS, define an own type and convert.
- Types own their behaviour: per-type logic (prompt, answer JSON schema, value parsing and
  validation) is a trait impl in the owning sdk. A consumer calls it and never re-implements it
  from a type-label string (data-view widget extraction lives on `DataViewComponent` in
  `assessment-sdk`; evaluation only calls it).
- Typed values across boundaries: events and gRPC messages carry the sdk type, never JSON in a
  `String` or a `serde_json::Value` (`payload: EvaluatedPayload`, not `payload_json: String`).
- Dependencies: an sdk depends only on `packages/*` and lower-layer sdks, never on any server
  crate. sdk→sdk edges form a DAG. Services may exchange events both ways, but a shared type lives
  only in the lower-layer sdk.
- The sdk is a separate package, not a lib/bin feature split of the server crate: Cargo detects
  cycles per package, so feature gates cannot break one.
- Build: the sdk is a member of its SCS's own cargo workspace (the root workspace excludes
  `services/*`). CI runs sdk tests and rebuilds every SCS that depends on a changed sdk. Its ts-rs
  output goes to the SCS's `ui/types/` through the SCS Makefile.

## What a change carries

- README rows updated for any new method, event, table, peer or setting.
- `make gen-ts` run after changing a route macro or a ts-rs type; the output is never committed.
- Version bumped in `package.json` when a versioned bundle's contents change (see CLAUDE.md
  "Versions"); `services/dataroom` and `services/assessment` are never bumped.
- A Playwright step in the persona journey that uses the feature
  (`playwright/tests/scenarios/*.spec.ts`), not a new per-feature spec.
- Scope: one user scenario or task, with every SCS it needs (CLAUDE.md "PR scope").
